# Правки цены, НДС и названия в preview

Первоначальные суммы и произвольные услуги до первого preview описаны отдельно: [INITIAL_REQUESTS.md](INITIAL_REQUESTS.md). Ниже — последующие правки. Дополнительно поддерживается «Во второй строке сумма 1200» как net-сумма строки; это отличается от unit price и от итога документа.

После получения preview пользователь может написать или наговорить:

- «Поставь цену 1500» — цена единицы без НДС в валюте текущего preview.
- «НДС 5%» или «НДС ноль процентов» — точная ставка, проверяемая по справочнику 1С.
- «Без НДС» — отдельный exempt-профиль, не подмена ставкой 0%.
- «Назови услугу Бухгалтерское обслуживание за ноябрь» — описание строки; ID услуги сохраняется.
- «Во второй строке цена 1500, НДС 5%» — правка конкретной строки.

Если строк несколько, для цены и названия нужен номер. Налог без номера применяется ко всем строкам. Повторяющиеся строки одной услуги не объединяются. Правки даты/количества сохраняют ручные значения; новый клиент, выбор другой услуги или нового исторического образца очищает их.

Для последующих правок нужен существующий preview; первоначальные параметры проходят отдельный baseline flow по ссылке выше. Net-сумма строки отличается от цены единицы, общий итог документа не распределяется автоматически. Цены с включённым НДС и конвертация валют пока не поддержаны. Неизвестная/неоднозначная ставка, неподтверждённый профиль, некорректное число или изменившиеся исходные строки блокируют правку. Примеры поддерживаемых чисел: `1500`, `1 500,50`, «тысяча пятьсот». Неоднозначное `1,500` не принимается.

## Вид цены исторического образца

Исторический price может уже включать НДС: preview явно показывает этот режим, цену с НДС и отдельные net/VAT/gross суммы. Пользовательская «Цена» и «на сумму» по-прежнему означают значения без НДС. Для такого образца сервер пересчитывает пользовательскую правку в native цену с НДС и принимает её только при точном обратном совпадении net/VAT/gross до копейки. Непредставимое при данном количестве значение требует уточнения; итог не подгоняется. Изменение только количества или ставки сохраняет вид исходной цены. Числа по-прежнему декодируются локально, налоговый профиль читается live, а подтверждение отзывается при любой правке.

## Реализация и границы

`LanguageIntent.preview_changes` содержит только индексы слов сообщения для цены/ставки/названия. `app/numbers.py` декодирует точное число без помощи модели; проверяются контекст числа, валюта и исходный текст. В реальном режиме AI видит признаки наличия полей, а не FirstBit строки, цены, IDs или названия. Модель не получает новых инструментов.

Номер строки сверяется с явной цифровой/порядковой ссылкой пользователя. Legacy tax_change также получает номер из текста локально. Явное «НДС ноль процентов» превращается в rate=0 независимо от ошибочной метки модели «without_tax»; это не exempt. Дублирование одного rename-span в catalog line_changes не добавляет строку: при явном переименовании остаётся только описание. Несовместимый запрос одновременно добавить/переименовать ту же услугу требует уточнения.

`InvoiceDraft` → `InvoiceCommand.preview_overrides` содержит пользовательские правки без provider IDs. `InvoiceService.prepare()` привязывает их к существующему клиенту, per-line `InvoiceLine.source_id` (либо primary `HistoricalProposal.source_id`) и `InvoiceLine.source_line_number` только внутри `ResolvedInvoiceCommand`. `BillingBasis` schema и `OneC` методы сохранены.

FirstBit сначала проверяет арифметику исходных posted-строк и их идентичность. Затем проверяет `Catalog_VATRates` и пересчитывает сумму строки и налог через Decimal с ROUND_HALF_UP до 0,01. Название не заменяет `Item_Key`. Ручные поля отмечаются в preview как предложение пользователя. Налоговый профиль подтверждает существование ставки и её тип, но не юридическую применимость к новому документу.

Используется уже проверенная metadata для `Catalog_VATRates`: `Ref_Key,DeletionMark,Description,Rate,Exempt,Export,OutOfScope,Calculated`, и `Document_InventoryExpense.Inventory.LineNumber`. Дополнительных объектов/полей, ItemPrices или новых бухгалтерских defaults нет. Поиск профиля ограничен фиксированным GET с typed rate или экранированным строковым литералом; пользователь не формирует OData syntax. Generic 0% не выбирает Export-профиль автоматически.

Любая попытка правки отзывает старую кнопку. Проверка preview заново читает источник и налог. Смена source ID/LineNumber блокирует перенос правки и требует подготовки нового baseline; изменение проверенных значений требует нового подтверждения. Обычный price/tax/name edit сохраняет operation ID и меняет digest/revision. GET-only provider и ручные fake proposals остаются неисполняемыми. В controlled writer правки допускаются только с новым полным ExecutionReview и явным подтверждением; изменение налога/учётных данных может оставить отдельный write blocker. Admission и фактический rollout принадлежат [PRODUCTION_OPERATION](PRODUCTION_OPERATION.md).

Runtime follow-up: одинаковые дубли одного поля от модели объединяются только при точном равенстве typed values; различные значения требуют уточнения. Явное «назови услугу …» превращает ошибочный legacy catalog-add ответ в display rename, сохраняя ID. Для единственной финальной rename-фразы полное название берётся дословно из текста, включая слово, пропущенное model span; номер строки проверяется по реальной rename-фразе. Ошибочная метка create исправляется на edit только при существующем preview, без нового клиента/счёта в запросе. Новые денежные значения или IDs не выводятся из этих исправлений.

## Естественные batch-правки строк

Редактор принимает одно или несколько действий в одном текстовом или голосовом сообщении: изменение количества, цены, НДС или описания; добавление, удаление и замена строки. Строку можно указать номером/порядковым номером из последнего preview или названием услуги. Совпадение разрешается локально; неоднозначная ссылка не выбирает строку автоматически. Например: «Строка 2 — 4 штуки, строки 3 и 4 удали».

В preview позиции показываются как «Пункт N». Все действия одной правки существующего preview передаются в `draft_changes`; `line_changes`/`preview_changes` остаются для совместимости с одиночными старыми запросами и не должны смешиваться в новом batch. Номера разрешаются по последнему показанному preview до удаления/перенумерации, поэтому например «удали пункты 2 и 3, в пункте 5 количество 5» меняет исходный пункт 5, а новый preview нумеруется заново. Одинаковые услуги из исторического счёта остаются раздельными учётными позициями; чтобы изменить одну из повторяющихся, указывают номер.

Для просьбы сохранить перечисленные услуги и убрать остальные intent использует `retain` для каждого явно названного пункта. Это применяется как одна атомарная правка; если хотя бы одну сохраняемую позицию нельзя разрешить однозначно, preview остаётся без изменений. Название допускает безопасное приблизительное сравнение с текущими preview-описаниями и локальными запросами; точное совпадение имеет приоритет, ничья остаётся уточнением. Пользователю можно назвать услугу вместо номера. Если одинаковые строки неразличимы по названию, требуется номер.

Языковая модель возвращает только типизированные операции и spans исходного текста. `app/intent.py` детерминированно проверяет ссылки, применяет пакет к стабильным внутренним ID строк, сохраняет происхождение исторических строк и пересчитывает поля через обычную подготовку preview. FirstBit перечитывает соответствующие source/LineNumber; если связь строки с исходной историей не подтверждается, подготовка прекращается. Повторяющиеся строки одной услуги остаются отдельными.

Для уже существующего draft упоминание счёта/цены не должно само по себе включать схему первоначального счёта. При явном edit-языке ошибочная модельная разметка existing line как `initial_lines` нормализуется в source-grounded preview mutation; target всё равно обязан разрешиться по текущему preview. Quantity извлекается из подтверждённого числа рядом с маркером количества/единицы, если модельный span захватил соседнюю цену; при нескольких возможных значениях запрос уточняется. Это не меняет правило: цена — явное значение пользователя, налог/суммы пересчитываются и проходят существующую проверку.

Старое подтверждение остаётся доступно при no-op, отклонённой или неоднозначной правке. После успешной правки выдаётся новый preview с новым digest и confirmation token; предыдущая кнопка получает понятный ответ и не запускает операцию. Preview conversation остаётся process-local и очищается при перезапуске; durable journal относится только к уже подтверждённым операциям.
